Executable environment DSL:
- environment.version must be exactly "text-exec-dsl-v0".
- environment.initial_state is a JSON object containing concrete synthetic entities that later trajectories may use.
- environment.tool_rules must contain exactly one rule for every tool name.
- Each tool rule has a non-empty branches list.
- Each tool rule should end with a catch-all branch such as {"if": true, "response": {"status": "failed", "error": "..."}} unless every possible valid call is intentionally covered by an earlier unconditional branch. Do not leave ordinary wrong arguments as interpreter-level "no branch matched" errors.
- Each branch has:
  - "if": a condition object, or true.
  - "response": the JSON response returned when the branch matches.
  - optional "effects": state updates after response creation.
- Tool responses in later trajectories must be derivable from this environment. Do not rely on invented tool outputs.
- Values required before the first retrieval/list/read response must be user-visible. For example, if open_resource.target, locate_file.file_name, authenticate.account_id, or authenticate.credential_value is required before any tool has exposed it, use a value that appears in the source text or workflow, or explicitly include it as a user-provided value in the workflow steps. Do not require hidden literals such as internal aliases, arbitrary file names, or synthetic account IDs that the Stage 3 model cannot know.
- Internal IDs may appear in initial_state, but a trajectory must be able to discover them through list_records, search_records, get_record, read_state, locate_file, create_upload_session, upload_resource, start_job, or another prior tool response before using them in later arguments.
- For user-facing resources, prefer branch conditions that accept the same visible names a user or workflow would say, such as "Ricoh MP C5503" rather than only "ricoh_scanner_interface". If an internal alias is useful, add a separate visible-name branch or expose the alias through a prior tool response.

Allowed condition operators:
- {"exists": "$state.collection[$args.arg_name]"}
- {"not_exists": "$state.collection[$args.arg_name]"}
- {"eq": ["$state.path", "literal_or_other_path"]}
- {"ne": ["$args.field", "literal_or_other_path"]}
- {"range": {"value": "$args.number_arg", "min": 1, "max": 10}}
- {"all": [condition, condition]}
- {"any": [condition, condition]}
- {"not": condition}

Allowed response/effect expressions:
- String paths: "$args.arg_name", "$state.collection[$args.id].field", "$response.output_id".
- Literal JSON values: strings, numbers, booleans, arrays, objects.
- Template strings: {"template": "job_${args.order_id}"}.
- Filter values: {"filter_values": {"from": "$state.collection", "where": condition_using_$item_and_$key, "select": "$key"}}.

Allowed effects:
- {"set": "$state.collection[$response.id]", "value": {...}}
- {"append": "$state.collection", "value": {...}}
- {"delete": "$state.collection[$args.id]"}

Effect constraints:
- Every effect target must be a path starting with "$state".
- Use "append" only when the target in initial_state is an array.
- If a collection is represented as an object keyed by id, use "set" with a dynamic key, e.g. {"set": "$state.photos[$response.copied_photo_id]", "value": {...}}.
- A "set" on an existing object with an object value shallow-merges those fields into the existing object. A "set" on a new key creates the object, and a "set" on a scalar field replaces that field.
- You may update individual fields with paths such as "$state.photos[$args.photo_id].edited", or merge several fields with "$state.photos[$args.photo_id]".
- Do not write bare paths such as "photos" or "orders"; always write "$state.photos" or "$state.orders[$args.order_id]".
- Include at least one initial_state case for each important branch in the text. If the text says a printer may fail and then another printer is tried, include one failing printer and one available fallback printer.
